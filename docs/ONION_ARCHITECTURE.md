# Луковичная архитектура SPIKE

Этот документ фиксирует целевое устройство проекта и решения для поэтапного рефакторинга. [Архитектура скриптов](SCRIPT_ARCHITECTURE.md) описывает текущую реализацию и подключения Unity. [ТЗ](GAME_DESIGN.md) задаёт правила игры.

## Слои и направление зависимостей

Зависимости в коде направлены к игровым правилам. Внешние слои могут использовать внутренние. Если сценарию нужно обратиться к хранилищу или управлять сценой, он может объявить нужный ему контракт, а внешний адаптер реализует его. Bootstrap связывает реализации с потребителями.

| Слой | Ответственность в SPIKE |
| --- | --- |
| Domain Model | Состояние и правила персонажей и попытки. Сюда относятся здоровье, допустимые переходы боевых состояний и условие допуска к боссу. |
| Domain Services | Игровые правила, которым тесно внутри одной модели. Возможный пример — обмен глобальными жизнями игрока и босса по ТЗ. Простые правила остаются у владельца состояния. |
| Application Services / Use Cases | Сценарии попытки. Например, начать миссию, применить сохранённый прогресс, поставить игру на паузу или завершить попытку. Сценарий определяет порядок действий и применяет правила домена. |
| Контроллеры и представления | Принимают команды от Unity Input System и кнопок, вызывают сценарии и отображают состояние. Контроллер кнопки и сценарий паузы выполняют разные роли, даже если оба названы контроллерами. |
| Инфраструктура Unity | Активация объектов, смена сцен, физика, масштаб времени, файловое хранилище и сериализация JSON. |

Развиваем существующие границы постепенно. В проекте уже есть модели персонажей, представления и репозитории. При этом часть боевого кода напрямую обращается к Unity. Например, [PlayerLocomotion](../Assets/_GameFiles/Scripts/Player/PlayerMovement/PlayerLocomotion.cs) использует `Time.deltaTime` и физические запросы. При рефакторинге внешних сервисов достаточно выносить такие зависимости там, где они пересекают границу конкретного сценария.

## Сборка и время жизни

- **Bootstrap** создаёт сервисы Application и Domain с нужным временем жизни, получает ссылки на компоненты Unity и связывает их. Состояние попытки создаётся заново для новой попытки. Один экземпляр сервиса можно передавать нескольким потребителям через конструктор или инициализацию. Это даёт общий объект без глобального `Instance`. Внутреннюю сборку компонентов персонажа можно оставить рядом с персонажем, если они используются только там.
- **GameController** — кандидат на координатор переходов миссии. Он может запускать попытку, применять восстановленный прогресс и координировать её завершение. Боевые правила, решения ИИ, запись файлов и отрисовка UI принадлежат соответствующим компонентам. Сейчас [GameController](../Assets/_GameFiles/Scripts/GameControllerScenes/GameController.cs) пуст.
- **Статика.** Поэтапно убираем глобальное изменяемое состояние, статические игровые события и глобальные точки доступа к сервисам. Связываем подписки со временем жизни издателя и подписчика. `const` и чистые функции можно оставлять статическими, поскольку они не хранят состояние сессии. При разборе начнём с конкретных владельцев, например урона, движения и поворота игрока.
- **MonoBehaviour.** Для каждого сервиса проверяем, нужны ли ему сериализованные ссылки, жизненный цикл, кадровые или физические callbacks Unity. При отсутствии такой причины используем обычный C#-класс и создаём его в Bootstrap. Доступ к Unity API сам по себе не требует наследования. Например, `ScenePausing` уже обычный класс, хотя работает с `Time.timeScale`.
- **События и Observer.** Издатель сообщает о факте, а потребитель решает, как на него реагировать. Для уведомлений, которые публикует сам владелец, используем `event` экземпляра. Когда отдельный класс состояния должен вызвать уведомление напрямую, используем публичный делегат экземпляра, как `Player.Idled`. Такой делегат доступен внешнему коду и для вызова, и для присваивания. Обязательный порядок действий сценария выражаем явными вызовами. Общая шина событий может пригодиться, если один факт нужно доставлять нескольким независимым подсистемам. Для счёта достаточно прямых подписок, которые собирает Bootstrap.

## Счёт в текущей реализации

[ScoreController](../Assets/_GameFiles/Scripts/ServicesGeneral/Score/ScoreController.cs) — обычный C#-класс на одну попытку. Он хранит очки за рядовых и бонусы за пары фаз босса. Общий счёт вычисляется из двух значений. Рядовой публикует `Died`, босс — `PhasePairCompleted`. Bootstrap связывает эти события со счётчиком и по `IsBossUnlocked` применяет к сцене правило двух очков за рядовых.

HUD получает начальное значение и подписывается на `ScoreChanged`. Итоговые экраны получают число при открытии. В сохранение идут очки за рядовых, а бонусы дуэли при загрузке сбрасываются. Этот пример задаёт границу между игровым правилом и адаптером Unity.

## Пауза в текущей реализации

`BootstrapTestScene` создаёт `UIController` и передаёт ему панели, `InputController`, `ScenePausing`, `ScoreController` и `GameSaveLoadInteractor`. Контроллер управляет паузой и вводом, показывает победу или поражение и вызывает очистку сохранения после победы. `SceneLoading` — обычный C#-сервис инфраструктуры Unity. Каждый Bootstrap создаёт свой экземпляр. На уровне один экземпляр обслуживает переходы из `UIController` и перезагрузку из интерактора сохранения. Он возвращает `Time.timeScale` к `1` при загрузке сцены, а при возврате в меню удаляет переживший переход `SoundDesign`.

## Сохранения в текущей реализации

`GameSaveLoadInteractor` — обычный C#-класс. Bootstrap передаёт ему репозитории и `ISceneSaveState`, а в `Start` запускает загрузку. Интерактор определяет порядок восстановления, `SceneSaveState` собирает и применяет данные объектов Unity. DTO сохраняют типы Unity для позиции и поворота и прежний формат JSON.
